Migrate whole app at once, or feature-by-feature?
Migrate it as one ROS2 node. Splitting JobMgr into per-feature ROS2 nodes is a bad idea here, for reasons visible directly in the coupling above:

One shared mutable state struct drives everything. Features #2, #4, #5, #11, #12, #13, #14, #15, #16, #18, #19 all read/write the same in-process 
currentTaskLoad/multi-task struct (LpsSaJobMgrTasks.h) within the same 100ms cycle. That's 11 of 21 features touching one shared object every tick.
 Splitting them across process/node boundaries means replacing direct C++ member access with IPC (topics/services) for what is currently a single 
 atomic in-memory update — that's a real redesign, not a lift-and-shift.
#1 (pass-tracker integration) is the central event loop. Nearly every other feature is downstream of its output each cycle. It can't be peeled off 
separately without becoming the de-facto "first phase" that everything else still blocks on — so isolating it buys you nothing.
#21 (SEA licensing) is a cross-cutting gate, not a subsystem — it touches #7, #9, #10, #11, #16, #17. You can't migrate it independently; it has 
to move with whatever it gates.
lps_pass_tracker is an external C library statically compiled into the JobMgr binary (not linked as a shared lib — see the earlier SConscript finding),
so it isn't a natural service boundary either.
