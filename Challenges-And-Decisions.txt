======================================================================
JobMgr & WeighApp -- SCS to ROS2/DDS Migration
CHALLENGES & DECISIONS LOG
======================================================================
Running record of real problems hit, how they were actually resolved,
and the evidence behind each decision -- not a plan, a record of what
already happened. Updated as work continues.

======================================================================
PART 1 -- ARCHITECTURE DECISIONS
======================================================================

1.1  Full rewrite vs. communication-only migration
----------------------------------------------------------------------
Two candidate approaches were compared: rewrite JobMgr/WeighApp as
pure ROS2 nodes, or swap only the communication transport and leave
logic untouched. Investigated what "full rewrite" would actually cost:
loss of native OEL real-time scheduling, WeighApp's independent
task_1x() OEL background task (NVM read/write) having no equivalent
in a pure-node design, watchdog servicing built into task::Task with
no automatic replacement, and a live launch/supervision mechanism
that would need building from scratch (currently solved for free by
staying on the AIS task supervisor).
DECISION: communication-only. Logic, scheduling, and NVM usage stay
exactly as-is; only the transport changes.

1.2  SCS/OEL are not "non-AIS" layers
----------------------------------------------------------------------
Early framing treated SCS and OEL as separate from "AIS proper."
Traced the actual repo layout: SCS (InputInterface<T>/OutputInterface<T>
+ scsIOContainer) and OEL both physically live inside eta-ais/
machineCommon, same as ais_task, ais_log, ais_config. There is no
non-AIS layer above raw OS/hardware.
DECISION: corrected the mental model before any further design work
proceeded on top of it.

1.3  Variant A -> Variant B -> final "full DDS boundary" design
----------------------------------------------------------------------
Three iterations, each driven by a real objection:
  - Variant A (pure rclcpp::Node, leave task::Task entirely): real
    ROS2 citizen, but reopens every cost in 1.1.
  - Variant B (apps stay task::Task, only SOME channels get DDS
    wrappers): avoids 1.1's costs, but rejected -- "I don't see ros2
    nodes and all, just you have changed communication from scs to
    dds... ros2 needs to be brought into the picture as a lead actor."
  - Final: apps stay task::Task (all of 1.1's guarantees preserved),
    but EVERY channel becomes a DDS wrapper -- zero raw SCS objects held
    by either app. The 4 JobMgr<->WeighApp shared channels go native
    DDS-to-DDS; everything else goes through one shared Bridge.
DECISION: final design adopted specifically because it's the only one
that satisfies both "ROS2 is a real, full participant in this app's
communication" AND "nothing about scheduling/NVM/watchdog needs
re-verifying."

1.4  Bridge count: one shared process, not one per app
----------------------------------------------------------------------
Considered per-app bridge instances vs. a single shared cpm_scs_bridge.
DECISION: one shared Bridge -- matches "one boundary, one seam"
framing, and its channel list is a visible, incrementally-growable
measure of migration progress as more apps eventually migrate.

PART 2 -- DATA VERIFICATION: MISTAKES CAUGHT AND FIXED
======================================================================
These are the cases where an earlier claim (mine or a pasted document)
turned out to be wrong, and what actually corrected it. Listed because
each one represents a real risk that shipped into a channel definition
before being caught.

2.1  jobmgr.txt (pasted reference document) was fabricated
----------------------------------------------------------------------
Claimed function name weigh_mode() (real: LpsPtUpdate()), wrong struct
field names, a false "PassCount < 50" horn threshold, a false claim
that WeighApp's task_1x() handles JobMgr's NVM writes (JobMgr has no
src_app/ at all), a wrong state machine, and "Bind all 10 SCS
channels" when the real, fully-cited count is 16.
RESOLUTION: never trusted without independent citation. Full 16-channel
list rebuilt from real bind()/fetch()/get()/publish() call sites,
written up in References/jobmngr_new.txt with file:line citations for
every one.

2.2  timePoint claimed dead everywhere -- wrong
----------------------------------------------------------------------
Verified (correctly) that LpsSaJobMgrTxChannel's timePoint is never
read back by any consumer -- constructed, serialized, never used.
Generalized this to "drop timePoint from all 16 channels" -- this was
wrong. LpsSaJobMgrRequestHelper.hpp and LpsSaWeighAppInf.hpp both
compare timePoint across Tx/Resp channel pairs for response-freshness
correlation (nextTxTimePoint_ = response.timePoint, then compared
against the Tx channel's own timePoint). The earlier "repo-wide grep"
claim was inaccurate -- only apps/LpsSaJobMgrApp had actually been
searched, not prod/common/interfaces/*RequestHelper.hpp.
RESOLUTION: LpsSaJobMgrTxChannel.msg and LpsSaJobMgrRespChannel.msg
(both already pushed) were corrected after the fact, with an honest
commit message explaining the mistake. Documented the real rule in
CHANNEL_MAPPING.md Part 3: timePoint is live wherever a
...RequestHelper.hpp/...AppInf.hpp companion class exists, dead
otherwise -- checked per channel, not assumed.

2.3  DataLinkDataInput matched to the wrong struct
----------------------------------------------------------------------
First pass matched it to eta-ais/.../legacy/common/interfaces/
CpmDataLinkData/DataLinkData.h, marked "uncertain match." That struct
is unrelated -- a coincidental name collision. The real resolution
path is interfaces/DataLinkData/InterfaceTypes.h (confirmed via the
actual #include in LpsSaJobMgrApp.h:46), which does not exist in this
checkout at all.
RESOLUTION: corrected in CHANNEL_MAPPING.md; the earlier "legacy
folder, complex map-based struct" entry was replaced with an accurate
"folder does not exist" status once the real include path was traced.

2.4  4th JobMgr<->WeighApp direct channel found late
----------------------------------------------------------------------
The original boundary diagram (and the whole "3 direct channels"
framing used through most of the design discussion) missed that
WeighApp calls LpsSaScsSendZeroRqst() (LpsSaScs.cpp:700-712), which
publishes directly onto LpsSaJobMgrReqstChannelOutput -- the same
channel JobMgr reads from the UI. This was found while doing the
file-level dependency walk for the wrapper work, not during the earlier
architecture discussion.
DECISION: corrected the direct-channel count to 4, not 3. This
channel is a HYBRID -- WeighApp's leg goes direct DDS, but the
legacy UI's leg still needs the Bridge, since aisJhm2RequestProc isn't
migrated. Both publish onto the same DDS topic.

3.1  WeighBktWtAccuracy_t -- reconstructed from indirect evidence

Real enum defined in lps_common (missing submodule). No file in this

3.2  LpsPublic.h fields (LpsSaWeighTxChannel) -- zero evidence, not blocked
----------------------------------------------------------------------
6 types (LpsWeighBktDigStat_t, LpsWeighCalStatus_t, LpsWeighBktDumpStat_t,

the real, still-compiled C++ enum in WeighApp's own code, so the

3.3  SwitchInputScsInput / OutputChannelOutput / DataLinkDataInput --

  - OutputChannel/OutputCmd: reconstructed from the one real

  - DataLinkData/DataLinkParam: confirmed to be a large, generic,

PART 4 -- PACKAGE STRUCTURE DECISIONS
======================================================================

4.1  cpm_common_interfaces split out of job_mgr_interfaces
----------------------------------------------------------------------
Several types (WeighBktWtAccuracy, TipOffTriggerType, TipOffState,
the Reqst/Resp Command enums, and eventually the whole
LpsSaJobMgrReqstChannel message family) were first drafted directly
inside job_mgr_interfaces. Mid-session, grepping for cross-app usage
(prompted by a direct question: "is any struct/enum used by/needed in
any other app?") found LpsSaWeighApp.h:256 uses
LpsSaJobMgrStandbyState_t directly, and WeighApp publishes directly to
LpsSaJobMgrReqstChannelOutput (see 2.4).
DECISION: created cpm_common_interfaces as a third package with no
dependents of its own; job_mgr_interfaces and weigh_app_interfaces
both depend on it, never the reverse. Required going back and moving
7 already-created files out of job_mgr_interfaces after the fact.

4.2  Field naming: snake_case is a ROS2 requirement, not a style choice
----------------------------------------------------------------------
Original plan said "field names kept identical to minimize downstream
diff." rosidl (ROS2's message generator) rejects camelCase/PascalCase
field names outright -- this was asserted before actually checking the
constraint. Confirmed by contrast with the real Caterpillar ROS1
precedent (ais_mc_msgs/MachineSN.msg, prod/coretech/aisBridge, 2019-2021):
that ROS1 system kept camelCase field names (machineSN, equipmentID) --
proving the constraint is specific to ROS2/rosidl, not a general ROS
rule this project chose to break.
DECISION: mechanical camelCase -> snake_case conversion for every
field, with an explicit old-name/new-name citation in each .msg file's
header so nothing drifts silently.

PART 5 -- BUILD & WRAPPER DESIGN DECISIONS
======================================================================

5.1  Does SCons need colcon to link rclcpp? -- No, but unverified until
     real evidence appeared
----------------------------------------------------------------------
Initial answer was reasoned from first principles: colcon is
orchestration, not a build requirement, so any build system that gets
the right -I/-L paths should link rclcpp fine. This was underspecified
until ROS2_custom_Code.zip (a real, user-provided example) was
inspected: build.sh does plain `cmake .. && make`, explicitly skips
ament_package(), and the zip contains real compiled build artifacts
proving it worked on ROS2 Jazzy.
DECISION: confirmed the mechanism (CMAKE_PREFIX_PATH/AMENT_PREFIX_PATH,
set by sourcing setup.bash) is what actually matters, not which build
tool reads it. SCons needs the same environment variables parsed into
CPPPATH/LIBPATH -- exact mechanism (pkg-config vs. manual paths, direct
rclcpp link vs. a dds_wrapper_runtime wrapper library) still open.
Real risk still unverified: A7H4 toolchain ABI compatibility with
ROS2 Jazzy's prebuilt binaries (GCC 13/glibc 2.39) -- needs a real
build environment, not more source reading.

5.2  PIMPL for RosInputInterface<T>/RosOutputInterface<T> -- fallback, not built
----------------------------------------------------------------------
Considered hiding rclcpp::Node/Publisher/Subscription behind a
forward-declared Impl class (pattern found in the same zip) to keep
<rclcpp/rclcpp.hpp> out of consuming headers.
DECISION: not used initially. PIMPL doesn't transfer cleanly to a
header-only template -- no single .cpp exists to hide Impl in; would
need a non-templated, type-erased base class the template forwards to.
Kept as an explicit, documented fallback in Development-Plan.txt,
built only if the plain approach causes a real, observed problem
(e.g. excessive compile-time/header bleed), not preemptively.

5.3  RosInputInterface<T>::get() -- queue, not a cached latest-value
----------------------------------------------------------------------
The same zip's subscriber example uses a single cached value
(has_new_msg_ + latest_msg_, overwritten on each new message). Real
SCS get() is called in drain loops everywhere in the actual codebase
(`while (channel->get(x)) {...}`) -- a single-value cache would
silently drop messages if more than one arrives between polls.
DECISION: backed by a real std::queue<T>.

5.4  No mutex needed in the wrapper -- a direct consequence of an earlier
     scheduling decision, not a new one
----------------------------------------------------------------------
The zip's subscriber spins on its own background thread, so it
genuinely needs a mutex (callback thread vs. caller thread race).
This project's wrapper doesn't have that race: executor_.spin_some() is
called synchronously from inside executive(), on the same thread that
then calls get() immediately after -- the callback is guaranteed to
have finished before get() runs. This is a direct payoff of the
earlier decision (1.3 final design) to keep DDS spinning tied to the
AIS task's own cycle rather than a separate thread.

PART 6 -- IMPLEMENTATION-LEVEL FINDINGS (Step 4.1, LpsSaJobMgrApp.h/.cpp)
======================================================================

6.1  Interface-type includes had to be KEPT, not removed
----------------------------------------------------------------------
Assumption going in: once a channel's raw SCS pointer type is replaced
by a wrapper, the old #include <interfaces/.../InterfaceTypes.h> line
should go too. Checked first: grepped for SimpleCalData_t,
DispBestBktWt_t, and the tip-off enums across the app folder, and
found LpsSaJobMgrSimpleCal.h/.cpp (an UNTOUCHED file) and
LpsSaJobMgrApp.h's own LpsJobMgrJobTrackerInfoTbl_t struct both depend
on these types transitively through that same include.
DECISION: kept every existing interface-type include. Only the
channel POINTER type declarations changed; the headers supplying the
underlying struct/enum definitions stayed exactly as they were.

6.2  checkSEAEnableStatus() -- a real method, not just a rename
----------------------------------------------------------------------
The AutonomyConditionDiagnosticsTxChannel block in executive() called
txData.checkSEAEnableStatus(element.status) -- a method that doesn't
exist on the new plain-data ROS2 message type (message types are pure
data, no methods). Rather than reimplementing the logic from guesswork,
found the real implementation: TxInterface.hpp:58, a static method,
switch-statement over SCL_PRMSW_FEAT_STATUS_* constants. Confirmed it's
static (doesn't need an instance) and that the header defining it
(TxInterfaceInputChannel.h -> TxInterface.hpp) was already kept per 6.1.
DECISION: called directly via its class name
(AutonomyConditionDiagnosticsTxInterfaceStorage::checkSEAEnableStatus(...))
-- same real logic, zero behavior change, nothing reimplemented.

6.3  weighAppInf_ deliberately left untouched, not silently converted
----------------------------------------------------------------------
weighAppInf_ (type LpsSaWeighAppInf) wraps the 3 direct JobMgr<->WeighApp
channels (WeighReqst/Resp/Tx), but it's defined in a SHARED header
(interfaces/LpsSaWeighReqstChannel/LpsSaWeighAppInf.hpp) outside
LpsSaJobMgrApp's own files -- not something Step 4.1 (scoped to
LpsSaJobMgrApp.h/.cpp specifically) should quietly reach into.
DECISION: left as raw SCS for now, flagged clearly in both files with
a comment pointing to Step 6 (Direct DDS Wiring) as where this gets
resolved, rather than either silently converting it (scope creep) or
silently leaving it unmentioned (silent gap).

6.4  Debug channel field names had to change, not just the channel type
----------------------------------------------------------------------
LpsSaJobMgrScsDebugOut->publish(txOut) populated txOut.currentState
and txOut.tipoffAssistActivationCount (camelCase, matching the old AIS
struct). The new job_mgr_interfaces::msg::LpsSaJobMgrDebugChannel type
uses current_state/tipoff_assist_activation_count (snake_case, per 4.2).
DECISION: this confirmed that "swap the channel type, keep everything
else identical" is only true at the call-site-syntax level
(->get()/->publish()) -- FIELD access inside the populated struct also
needs updating everywhere a message gets constructed, which is real,
distributed work across every publish call site, not a one-time
mechanical pass.

6.5  HORN_PORT_NUMBER and PORT_ON/PORT_OFF/NO_FLASH -- real hardware
     values with zero evidence, not treated the same as a data-only enum
----------------------------------------------------------------------
#define HORN_PORT_NUMBER OutputChannel::Port::OUTPUT_SINK_3 (comment:
PIN29_GPIO88) and the PORT_ON/PORT_OFF/NO_FLASH constants used to build
the horn-output command have no numeric value anywhere in this
checkout -- confirmed by repo-wide grep, same as the other reconstructed-
from-usage types (Part 3.3). The difference: this one drives a real
GPIO pin, not just an internal data field.
DECISION: did not apply the usual "raw int, wrapper casts the real value
through at runtime" reasoning here, because there IS no real compiled
enum on the other side to cast from anymore -- the whole Port/State/
ChangeDuration type was reconstructed, not preserved. Used obviously-
fake sentinel values (0xFF, 0xF0, 0xF1, 0xF2) with loud "DO NOT
HARDWARE-TEST UNTIL FIXED" comments at both the #define and the call
site, specifically so this cannot be mistaken for a verified value or
silently drive the wrong pin during hardware bring-up.

6.6  WeighBktWtAccuracy/TipOffState/etc. are nested messages, not
     scalars -- every assignment needs `.value`
----------------------------------------------------------------------
These were promoted to shared "enum-as-message" types
(cpm_common_interfaces, Part 4.1) with the shape `{ constants..., uint8
value }`, not plain uintN fields. Assigning to them (e.g.
txOut.truck_weight_accuracy = someEnum) doesn't compile -- it has to be
txOut.truck_weight_accuracy.value = static_cast<uint8_t>(someEnum).
Caught while converting LpsSaJobMgrScsTx(), which touches 6 fields of
this shape in one function.
DECISION: every nested-type assignment gets an explicit static_cast
from the real, untouched AIS enum plus a .value accessor -- consistent,
not worked around per-field.

6.7  simpleCal_.getSimpleCalData() -- a real container-type conversion,
     not a field rename
----------------------------------------------------------------------
Untouched business logic (LpsSaJobMgrSimpleCal.h/.cpp) fills a
std::deque<SimpleCalData_t>& out-parameter. The new message's
simple_cal_data field is a ROS2 array, which generates as
std::vector<job_mgr_interfaces::msg::SimpleCalData> -- different
container AND different element type. Passing the new field directly
as the out-parameter doesn't compile.
DECISION: kept simpleCal_.getSimpleCalData() calling into a local,
OLD-typed std::deque<SimpleCalData_t> (business logic stays completely
untouched, exactly as planned), then explicitly converted
element-by-element into the new message's vector. This is the general
shape any future "untouched business logic fills an old container"
call site will need -- not a one-off.

6.8  get_tz_struct() -- traced through a submodule, called via its
     lower-level overload instead of reconstructing ShmClock
----------------------------------------------------------------------
tes_common_ais::get_tz_struct() is not declared anywhere inside
CPM-Loader-ais. Repo-wide grep initially came up empty; broadening the
search to the full eta-ais tree found it in
eta-ais/prod/machineCommon/content/prod/common/ais_chrono/tz.hpp
(already transitively reachable via <chrono/tz.hpp>), with two
overloads: a byte-array+size overload doing the actual timezone
decode, and a ShmClock&-taking overload that just calls
shmClock_in.get_TZ(tz_data) then forwards to the first. Reconstructing
ShmClock (a real class from the same submodule, not present in this
checkout as a header) to call the second overload would have meant
guessing its shape.
DECISION: called the byte-array overload directly --
tes_common_ais::get_tz_struct(shmClock.tzone_info.data(),
shmClock.tzone_info.size(), tzone) -- using the raw tzone_info bytes
already preserved verbatim in ShmClockInput.msg. No reconstruction of
ShmClock needed. Same session also converted get_UTC_offset() ->
utc_offset_min and get_SHM() -> shm_sec, both confirmed as trivial
field accessors.

6.9  DataLinkParam::DATA_LINK_PARAM_IDENTIFIER_PID -- another
     unverified hardware/protocol placeholder
----------------------------------------------------------------------
LpsSaJobMgrScsDataLinkDataRead() compares
dlParam.GetParamIdentifierType() against
DataLinkParam::DATA_LINK_PARAM_IDENTIFIER_PID. Repo-wide grep found
only two enumerator NAMES anywhere in the tree
(DATA_LINK_PARAM_IDENTIFIER_PID and _CAT_EXT, the latter in
DataLinkDataScsRx.cpp) -- no numeric value for either, and the
DataLinkParam struct itself isn't present in this checkout (see
DataLinkParam.msg header for the full partial-reconstruction
rationale, scoped to only the 3 PIDs JobMgr itself reads).
DECISION: same treatment as HORN_PORT_NUMBER/PORT_ON/PORT_OFF/
NO_FLASH -- an obviously-fake local constexpr sentinel (0xF3) with a
loud "UNVERIFIED PLACEHOLDER" comment, never a plausible-looking
guess. This is now the second call site needing this pattern; if a
third comes up, worth considering a single named convention (e.g. a
shared UNVERIFIED_PLACEHOLDER header) instead of repeating the comment
block each time.

6.10  LoadRecordOutput (Step 4.3, LpsSaJobMgrProcess.cpp) -- the
      business-logic type is too large to convert at declaration; only
      the publish() boundary gets converted
----------------------------------------------------------------------
LpsSaLoadRecordChannel (Datum<LpsSaLoadRecordChannelStorage>) is not a
plain-data struct -- it has real methods (getSubtotalByIndex(),
subtotalCount(), storeAction(), disableLists(), getCurrentSubtotal(),
etc.) that LpsSaJobMgrPtUpdate() calls throughout to build up a load
record (remove empty subtotals, set store action, apply zero/cal
adjust, add to simpleCal_). Unlike smaller channels, converting the
local variable itself to the new message type at declaration was not
an option -- none of those methods exist on a plain-data message, and
reimplementing them would violate the "logic stays untouched" decision
(1.1).
DECISION: kept `LpsSaLoadRecordChannel loadRecord;` as the OLD type for
the entire function body (unchanged), and added a one-shot
ConvertLoadRecord() (plus per-nested-type helpers
ConvertLoadRecordSubtotal/Pass/TimeStamp, anonymous namespace, local to
LpsSaJobMgrProcess.cpp) called only at the actual
`loadRecordOutputChannel_->publish(...)` call site. This is the
general pattern for any future channel whose old-side type carries
real business logic, not just data: the OLD type owns the logic
end-to-end, and exactly one conversion happens at the DDS boundary,
as late as possible.
Also confirmed (grep) that LpsSaJobMgrApp.cpp's loadOldLoadRecord()
NVM-load path (App.cpp:320-325) never crosses the DDS boundary at all
(no publish/get call in that flow) -- correctly left as pure old-type
file I/O, no conversion needed there.

6.11  LpsSaWeighAppInf.hpp (Step 6.1) -- the boost::signals2
      callback-driven blocking wait has no equivalent under the wrapper,
      so it was redesigned, not just retyped
----------------------------------------------------------------------
This shared header (prod/common/interfaces/LpsSaWeighReqstChannel/
LpsSaWeighAppInf.hpp -- outside the original 10-file list, deliberately
deferred from Step 4, see 6.3) wraps JobMgr's 3 direct-DDS legs to
WeighApp (LpsSaWeighReqstChannelOutput/RespChannelInput/TxChannelInput).
Under real SCS it used boost::signals2 addNewDataSlot() callbacks,
firing on a background SCS thread, so waitForTxData()/waitForResponse()
could genuinely block on a std::condition_variable until that callback
woke them or a timeout elapsed. ros2_wrapper::RosInputInterface<T>
(RosInputInterface.h) has no callback mechanism at all -- its
subscription just fills a std::queue<T>, drained by get(), and that
queue is only ever populated once per tick, synchronously, during
executor_.spin_some() at the top of executive(), on the same thread
that then calls into this class. There is no background thread left to
notify a blocked waiter; a condition_variable wait here would just
block for the full 250ms timeout, every tick, for zero benefit (nothing
new can arrive while blocked -- spin_some() already ran before this
class's methods are called).
DECISION: rewrote the class as pure single-shot polling -- every method
checks whatever spin_some() already delivered this tick and returns
immediately, no waiting. waitForTxData() now drains responseInput_
first (to tighten the freshness gate once the matching response
arrives, same logic as the old notifyResponseInput() callback, just
called synchronously instead of asynchronously) and then txInput_,
preserving the original "is this tx data new enough to reflect our
request" freshness check (txData_.time_point_ns >= nextTxTimePointNs_).
Also dropped waitForResponse()/sendRequestWaitForTxData()/
sendRequestGetResponse()/getLastResponse() and the string-based
InterfaceDb-bind start() overload: grepping every caller in this
checkout (LpsSaJobMgrApp.cpp:289, LpsSaJobMgrScs.cpp:883,1243) shows
only the pointer-based start(), sendRequest(), and waitForTxData() are
ever actually used -- the rest were already dead code before this
conversion, and porting them forward would just leave un-triggerable
condition_variable waits (nothing will ever notify them) sitting in
the tree as a future deadlock waiting to happen if anyone wired them
up. getNextAppRequestId() (was a static method on the old
LpsSaWeighReqstChannel Datum type, not present on the new plain-data
message) was inlined as a private static atomic counter, identical
logic to the original (LpsSaWeighReqstChannel.h:113-116).

6.12  General rule for inline-constants vs. own-package .msg file vs.
      cpm_common_interfaces promotion (asked explicitly, never written
      down before -- derived from comparing TipOffTriggerType_t vs.
      ReqPloadCtrlSysStat_t/ReqPloadOpMode_t, both in
      LpsSaJobMgrTxChannel.h)
----------------------------------------------------------------------
ReqPloadCtrlSysStat_t and ReqPloadOpMode_t both got inlined as local
named uint16 constants directly inside LpsSaJobMgrTxChannel.msg (not
promoted anywhere), even though both names also appear in
AutonomyConditionDiagnostics.cpp. Checked exactly how: that file does
`static_cast<ReqPloadCtrlSysStat_t>(PidWrD10972)` / `static_cast<
ReqPloadOpMode_t>(PidWrD10748)` -- decoding a raw J1939 PID value read
from DataLinkData, entirely independent of LpsSaJobMgrTxChannel. Same
C++ enum NAME reused in unrelated business logic, never the same DDS
message crossing a channel boundary -- no other .msg file ever needs
either type as a field, so nothing to gain from a shared file.
TipOffTriggerType/TipOffState (same header, right next to the above)
went to cpm_common_interfaces instead, because they're genuine
struct-FIELD reuse across two different real channels: LpsSaJobMgrTxChannel
(tip_off_trigger_type/tip_off_state/tip_off_state_cfg) and the separate
LpsSaJobMgrReqstChannel (data_tipoff_trigger_type/data_tipoff_mode).
StandbyState is carried by only ONE channel (LpsSaJobMgrTxChannel, a
single field) -- unlike TipOffTriggerType's 2-channel reuse -- so its

  1. Inline as local constants in the one .msg field that needs them --
     when the real type is a field in exactly one channel, AND any
     other appearance of the same C++ name never actually crosses a
     DDS boundary (ReqPloadCtrlSysStat_t's AutonomyConditionDiagnostics.cpp

     consumer).

     weigh_app_interfaces -- when a type is a field in 2+ channels
     within the SAME app (one source of truth instead of duplicated
     constant blocks) -- e.g. TipOffTriggerType/TipOffState.
  3. Promote to cpm_common_interfaces -- whenever the value genuinely
     crosses the JobMgr<->WeighApp app boundary and is read/compared/
     propagated on the far side -- regardless of how many channels
     carry it. One channel is enough if the OTHER app is a real
     consumer of that field (StandbyState: one channel, but WeighApp
     directly subscribes to it and acts on the value).

type" or "is this C++ name used in more than one file" -- it's "does
the same real value cross the app boundary and get genuinely consumed

something unrelated." That's the only test that survives both
counterexamples (ReqPloadCtrlSysStat_t: same name, no boundary crossing,
stays local; StandbyState: one channel, genuine boundary crossing,
