Step 1 — For each of your 3 channels, find where each app touches it.

Open VS Code's workspace search (Ctrl+Shift+F), scope it to the app's folder (there's a filter box under the search bar — type apps/LpsSaJobMgrApp/** or right-click the folder → "Find in Folder"), and search for how the channel gets registered:

InterfaceDb::fetch("LpsSaWeighReqstChannel
(Try both — different apps use different patterns, as you saw: JobMgr uses fetch+dynamic_cast, WeighApp uses bind.) This string search finds the exact line where the channel gets wired up, which immediately tells you the local variable or member name being assigned.

Step 2 — If Step 1 finds a member directly in the app's .h file, you're done finding it. If it doesn't, check whether it's being handed into a helper class.

Like you just saw with LpsSaWeighReqstChannel on JobMgr's side: the construction line exists in the .cpp, but there's no persistent member in the .h for it — instead the constructed object gets passed as an argument into another object's method (weighAppInf_.start(getTaskName(), requestOutput, responseInput, txInput)). When you see a locally-constructed variable get passed into another class's method like that, open that class's header (Ctrl+click on weighAppInf_'s type, or on .start(, jumps you straight to LpsSaWeighAppInf.hpp) and repeat Step 1 inside that file.

Step 3 — Once you have the real member name, find every place it's used.

Right-click the member name → Find All References (or Shift+F12). If the C/C++ extension's IntelliSense is fully configured for this codebase this is exact; if not, fall back to Ctrl+Shift+F searching the exact member name across the app's whole folder (not just the .h). Either way, this gives you every function that touches it.

Step 4 — For each function that shows up, read the whole thing and ask: does it also reference any other channel's member?

This is the one manual judgment step. First, go back to the app's .h and note every other channel member name declared near yours (usually grouped under a comment like /*SCS Interfaces*/ or /*Interfaces*/). Then, with the function open, use Ctrl+F (find-in-file, not workspace search) to check each of those other names against the function body. Two outcomes:

None found → the function is single-purpose, safe to convert whole.
Found → the function is tangled (like JobMgr's LpsSaJobMgrScsChkForReqst(), which also touches SwitchInputScs and displayStateInput_). Flag it — don't hand-edit it without real care, since a partial edit inside a shared function is where mistakes hide.
Step 5 — Do Steps 1–4 for both ends of the channel — the app that publishes it and the app that subscribes to it — independently. A channel only counts as "clean" if both ends check out. This is exactly what caught LpsSaJobMgrTxChannel (leg 5) being clean on JobMgr's publish side but tangled with DemoAppTxChannel on WeighApp's receive side — you'd have missed that if you only checked one direction.

Step 6 — Once every function is classified, your file list falls out directly:

The .h file that declares the member (or, if wrapped, the helper class's header) — always needs the type change.
The .cpp file with the constructor initializer list and initialize()/construction code — always needs the trivial "how it's built" change (new node/executor setup, new ros2_wrapper::... in place of the old bind/fetch).
Only the specific business-logic .cpp files containing functions you classified as "clean" in Step 4 — nothing else in those files, and no file that only contained tangled functions.
Step 7 — Don't forget the trivial connective tissue. Every member you retype also needs its constructor init-list entry and null-check/error-log lines updated to match (same pattern, just following the new type) — these show up automatically once you've done Step 3's reference search, so you won't miss them, but they're easy to mentally file under "business logic" when they're really just plumbing that has to stay consistent.

That's the whole method — it's the same 7 steps regardless of which channel or which app you're starting from.
