======================================================================
JobMgr & WeighApp -> ROS2/DDS Communication Migration
STEP-BY-STEP DEVELOPMENT PLAN
======================================================================

SCOPE (confirmed, final architecture)
----------------------------------------------------------------------
- LpsSaJobMgrApp and LpsSaWeighApp remain task::Task / SConscript-built
  binaries. No new class, no new process, no new launch mechanism, no
  change to scheduling/OEL/NVM.
- Every channel on both apps becomes a DDS-backed wrapper. Zero raw SCS
  objects remain inside either app. Both apps are fully stripped of
  direct SCS relations.
- JobMgr <-> WeighApp shared channels go native DDS-to-DDS directly,
  no bridge. Confirmed count: 4 whole channels, plus a 5th channel
  (LpsSaJobMgrTxChannel) that keeps its Bridge leg for the legacy UI
  but has 4 individual fields consumed directly by WeighApp too --
  see Step 6.1.5, added after independent verification against both
  apps' real .rb Interfaces config (Challenges-And-Decisions.txt 6.16).
- Every other channel (JobMgr: 12 of 16 remaining; WeighApp: its other
  ~19 channels) routes through ONE single shared cpm_scs_bridge
  process -- the only new binary in the whole system, and the sole
  SCS<->DDS translation seam.
- Nothing is deleted from the existing JobMgr/WeighApp source trees.
  Raw SCS types/includes are swapped for wrapper types inside the files
  listed below; the underlying AIS SCS machinery stays in the repo
  untouched because other (unmigrated) apps and the Bridge itself
  still depend on it.

STEP 1 -- Foundation (shared infrastructure, build once)
----------------------------------------------------------------------
1.1  Toolchain/ABI validation: confirm chosen platform's GCC/glibc are
     ABI-compatible with ROS2 Jazzy (GCC 13 / glibc 2.39 / C++17).
1.2  Create the colcon workspace. Package layout is intentionally
     small:
       - job_mgr_interfaces      (.msg/.srv only)
       - weigh_app_interfaces    (.msg/.srv only)
       - cpm_scs_bridge          (the Bridge)
       - (optional) dds_wrapper_runtime  -- see 1.4
     There is NO job_mgr_node / weigh_app_node package -- JobMgr and
     WeighApp stay in the existing SConscript build.
1.3  Wire SConscript's CPPPATH/LIBPATH to reach the colcon install
     space, and add the rclcpp/DDS link dependency. rclcpp is not a
     single library -- it pulls in rcl, rmw, the chosen rmw
     implementation, rosidl_runtime_c, rosidl_typesupport_cpp,
     rcutils, rcpputils, ament_index_cpp, etc. ament_cmake resolves
     this automatically via find_package(); SCons does not, so this
     has to be done manually (pkg-config if available, or explicit
     CPPPATH/LIBPATH/LIBS).
1.4  DECISION POINT: build a small wrapper library (its own tiny
     ament_cmake package, e.g. dds_wrapper_runtime) that internally does
     find_package(rclcpp) properly and exposes one narrow, stable C++
     API + one .so for SCons to link -- insulating SCons from rclcpp's
     internal dependency churn across ROS2 releases. Recommended, not
     yet finalized -- confirm before Step 3.
1.5  Decide ROS_DOMAIN_ID / discovery config shared by all three DDS
     participants (JobMgr, WeighApp, Bridge).
1.6  Bridge skeleton: task::Task subclass + embedded rclcpp::Node,
     spun via executor.spin_some() each executive() tick -- extend the
     existing cpm_scs_bridge/WeighScsRosBridge.hpp prototype rather
     than starting from scratch. No real channels wired yet.

STEP 6 -- Direct DDS wiring: JobMgr <-> WeighApp (no bridge)
----------------------------------------------------------------------
6.1  5 channel-legs go native DDS-to-DDS once both apps have wrappers.
     3 of these are pure direct (no Bridge involvement at all); the
     4th and 5th are HYBRIDs that also keep a Bridge leg (see 6.1.4
     and 6.1.5):
       1. LpsSaWeighReqstChannelOutput/Input   (JobMgr -> WeighApp)
          -- pure direct
       2. LpsSaWeighRespChannelOutput/Input    (WeighApp -> JobMgr)
          -- pure direct
       3. LpsSaWeighTxChannelOutput/Input      (WeighApp -> JobMgr)
          -- pure direct
       4. LpsSaJobMgrReqstChannelOutput/Input  (WeighApp -> JobMgr,
          confirmed live at LpsSaScs.cpp:700-712, previously
          uncounted -- see Step 2.5) -- HYBRID: this is the same
          channel JobMgr already reads as ReqstChannelInput from the
          legacy UI (aisJhm2RequestProc) via the Bridge. WeighApp's
          leg goes direct; the UI's leg still needs the Bridge, since
          the UI itself isn't migrated. Both publish onto the same
          ROS2 topic JobMgr subscribes to.
       5. LpsSaJobMgrTxChannelOutput/Input     (JobMgr -> WeighApp) --
          HYBRID, but a different shape than #4: same publisher (JobMgr)
          on the same topic either way, not two different publishers.
          The channel carries ~100 fields total; only 4 of them
          (standby_state, tip_off_state, tip_off_state_cfg,
          tip_off_trigger_type) are genuinely read by WeighApp's own
          business logic (confirmed via the real jobMgrIn drain in
          LpsSaWeighApp.cpp, and independently re-confirmed against
          both apps' real .rb Interfaces config -- see
          Challenges-And-Decisions.txt 6.14/6.16). Those 4 fields'
          types live in cpm_common_interfaces; the channel message
          itself stays in job_mgr_interfaces and keeps its Bridge leg
          to reach the legacy UI/DisplayApp for its other ~96 fields
          -- still counted as 1 of JobMgr's 12 Bridge-routed channels
          in Step 7.1, same as channel #4's UI leg is.
6.2  Agree topic/service names and QoS between the two tracks.
6.3  Validate the loop with both apps' component tests running
     together, still no bridge.

RESOLVED DECISIONS
======================================================================
  1. RosInputInterface<T>/RosOutputInterface<T> (Step 3) will NOT use
     PIMPL initially -- <rclcpp/rclcpp.hpp> is allowed to show up
     wherever the wrapper headers are included. PIMPL doesn't transfer
     cleanly to a header-only template (no single .cpp to hide Impl
     in -- would need a non-templated, type-erased base class the
     template forwards to), so it's kept as an explicit FALLBACK, not
     built preemptively: only implement the type-erased PIMPL version
     if the plain approach causes a real, observed problem (e.g.
     excessive compile-time/header bleed into the AIS SConscript
     build), not on spec. Reference implementation pattern for both
     the plain and PIMPL approaches: a real working ROS2 Jazzy
     pub/sub example (plain CMake, no colcon, rclcpp::spin_some()
     validated) -- see ros2_ws/ commit history around
     "ROS2_custom_Code.zip" investigation for the source.
  2. RosInputInterface<T>::get() will use a real queue (std::queue<T>),
     not a single cached latest-value -- SCS's real get() is called in
     drain loops everywhere in the existing codebase
     (`while (channel->get(x)) {...}`), so multiple messages arriving
     between polls must all be retrievable, not just the newest.
  3. No mutex needed inside the wrapper for the spin_some()-in-executive()
     model: spin_some() and get() run on the same thread, sequentially,
     inside one executive() tick -- the subscription callback finishes
     before get() is ever called, so there's no actual data race to
     guard against (unlike a background-thread-spin design, which
     would need one).
